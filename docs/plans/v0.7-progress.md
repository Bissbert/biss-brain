## Phase 2 — provenance and poisoning defence (2026-10-26) ✅

- 2.1 Model (`scripts/provenance.py`): every chunk has `source`, `trust` and `taint`. The meta
  schema has one definition. `/remember` writes `user` provenance only.
- 2.2 Capture reads the transcript by block and role. Tool results are tagged by tool name
  (WebFetch/WebSearch/MCP → `web`, Read/Grep → `file`, anything else → `tool`). The distiller
  tags each bullet with its source, and each source gets its own chunk. `<private>` spans are
  dropped at capture.
- 2.3 Taint propagates: trust is the minimum and taint the union through reconsolidation, arcs,
  daily roll-ups and global promotion.
  - Merges, arcs and roll-ups only combine one trust class (first-party vs tool/web), so web
    content cannot launder into a trusted summary.
- 2.4 Read-side policy:
  - Tool/web-tainted rows and rows with unknown provenance are never auto-injected. This
    covers SessionStart, UserPromptSubmit (filtered before the top-k cut) and PostCompact.
  - In search, tool/web scores are multiplied by 0.6. Recall, MCP and the UI show a
    `[source: X]` label.
  - A less trusted memory never supersedes a more trusted one. It is DEFERred without a judge
    call, in flush and in the dream sweep.
  - Low-trust text that reads like an instruction is stored as `kind=quarantine`.
    - It is never merged or judged.
    - It is hidden from model-facing search, inject, global recall and `related_to`. MCP
      refuses `kind=quarantine`.
    - It is visible through `/recall --kind quarantine` and in the UI.
- 2.5 Injected context is data: each memory is a `<brain-memory source= trust= date= kind=>`
  block under "Recalled notes from earlier sessions; reference only."
  - The text is entity-escaped, so it cannot close the frame or open `<system>`.
  - Attributes are validated, not copied.

## Phase 3 — temporal validity (2026-10-26) ✅

  so Lance needs no migration.
  - `superseded_by` stays the link. When it names an existing chunk, the row was contradicted
    and keeps its history. When it names no chunk, it is a tombstone (forget or UI delete) and
    the row is gone for every query, historical ones included.
  - The migration backfills `invalid_at` for existing contradictions only, as the successor's
    event time. Tombstones and cross-project links stay NULL.
- Writes:
  - flush CONTRADICTS: `old.invalid_at = new.valid_from`. It is never earlier than the old
    row's own `valid_from` and never deletes anything.
  - flush EXTENDS adds an `extends` edge.
  - The dream sweep orders each pair by event time, so the newer memory always supersedes,
    whichever was stored first.
  - New chunks get `valid_from` from the event's enqueue time. Arcs and dailies get the
    earliest member's time, not the dream run time.
- Reads:
  - `retrieve(as_of=T)` searches all rows in the project and keeps those valid at T

## Phase 4 — core memory tier (2026-10-26) ✅

- Storage (`scripts/core.py`), decision D4 (layered):
  - `~/.claude/brain/core/_global.md` and `<repo>.md` (private, the default). The frontmatter
    holds the repo path and the remote URL with credentials removed. A moved repo re-links by
    its remote.
  - The core dir is its own git repo, committed on every change. Commits pass identity,
    `commit.gpgsign=false` and `--no-verify` per command and never read or change the user's
    git config. Every git call has a 5 s timeout. `*.proposed.md` is git-ignored.
  - Shared layer: `<repo>/.claude/brain/CORE.md`. We never commit inside the user's repo.
- Format: `## Decisions / Conventions / Lessons / Pinned`, and each bullet ends with
  `<!-- m:<id> <date> <source> -->`.
  - A hand-written bullet gets an id from its text and source `user`. An unknown source tag
    reads as `imported`, never `user`.
  - Hand edits are committed at the next session start. A file with a secret-shaped line
    (anywhere outside the frontmatter) is never staged, by that commit or any later
    programmatic one. Doctor flags it and the line is never rewritten. Injection and
    `/core show` scrub on read.
  - Only column-0 bullets are items; indented sub-bullets and free text are kept verbatim.
- Index: `~/.claude/brain/core.sqlite` (outside the git repo), re-read when a file's mtime
  changes. It keeps one row per item version (`valid_from` / `invalid_at`). A changed line opens
  a new version, and a deleted line retires the item. Core is not in the Lance chunks table, so
  reconsolidation, the judge, decay, RIF/STDP and search never touch it.
- Injection: at SessionStart (startup, resume, **clear**, compact), ahead of recalled memory.
  - The text is escaped `<brain-memory kind="core" layer=… section=…>` blocks. Shared items are
    labelled `repo`.
  - The unit is the bullet: at most `core.max_items` (200), project layers first. Extra items

  - Cold projects get core too. The path makes no network or embed calls and fails closed to no

## Phase 5 — cost and latency (2026-10-26) ✅

### 5.1 Calibrated prompt-injection gate
- **The old gate.** Absolute cosine ≥ 0.5, top 2.
  - Precision was 0.46 (real) and 0.38 (synthetic).
  - No cosine-only setting reached 0.7 on both suites without dropping the hit rate to about 0.1.
- **The new gate** (in `retrieve.inject_gate`). Cosine ≥ 0.6 OR BM25 ≥ 7, top 1, 6,000-char budget.
  - It is fit by `scripts/eval/calibrate_inject.py`, which replays the gate on candidates recorded before gating by `run_eval.py`.
  - BM25 turned out to separate relevant memories from unrelated ones much better than cosine.

  | Suite | Precision (95 % CI) | Hit rate | Off-topic abstention | False injections | Poison |
  |---|---|---|---|---|---|
  | Real | 0.81 (0.62–0.91) | 0.57 | 0.94 | 0 | 0 |
  | Synthetic | 0.75 (0.51–0.90) | 0.46 | 1.0 | 0.09 | 0 |

- **Precision is in-sample.** It is the best of about 430 settings, scored on the same suites.
  - Fit on one suite and scored on the other, precision is 0.68 or 0.60.
  - With 16–26 injected items per suite, the intervals are wide.
- **No query vector.** If the embed misses its budget, the gate uses BM25 ≥ 7 alone: precision 0.77 (real).
- **BM25 depends on corpus size.** On the 50-row synthetic corpus the lexical side rarely fires.
  - After the D8 fresh start the gate is effectively cosine-only until the store grows.
  - Phase 8 follow-up: re-fit after D8.
- **Eval additions:**
  - 20 off-topic prompts per project (`tests/fixtures/eval_offtopic.jsonl`), with an `offtopic_abstain` metric;
  - a `novec` variant;
  - per-question `inject_cands`.
- **Trivial prompts are skipped:** slash commands, `!`, acknowledgements, fewer than 3 words.
- **Config renamed** to `inject_*`. The old `user_prompt_inject_*` keys are still read.

### 5.2 Hook hardening
- **Embed budget and deadline.** The embed budget is 300 ms; past it, the BM25 gate decides.
  - Retrieval runs on a worker under a hard 2.5 s deadline, counted from process start.
  - On a miss the hook prints nothing and calls `os._exit`.
- **Session ledger** at `<project>/sessions/<sid>.injected`.
  - SessionStart resets it, except on resume. Compaction also resets it.
  - Session ids are validated. Ledgers expire after 7 days.
  - Memories whose text is already a core item are skipped.
- **Side effects.** A proactive injection only touches `last_accessed`.
  - No retrieval_count, STDP, RIF or labile stamp: the model didn't ask for it.
  - So it can't feed dream's 2c core proposals.
- **Kill switch:** `/biss-brain:inject off|on|status`, stored as `<project>/inject.off`.
- **Metrics.** Each run appends to `inject_metrics.jsonl`: outcome, ms, embed ms, vector used and count. No prompt text.
  - Doctor warns when p95 exceeds 800 ms, when more than a quarter of prompts miss the embed budget, or when the deadline is hit.
- **Ollama `keep_alive`** is set (`embed.keep_alive`, 30m).
- **Lazy lancedb import.** `import lancedb` takes about 0.8 s and was at module top.
  - So every prompt paid it, including with injection off (the default) and for trivial prompts.
  - It now loads only on the full path. Disabled, killed and trivial prompts take ~70 ms wall clock.
  - A test checks with `-X importtime` that lancedb isn't loaded on those paths.

### 5.3 Default on? No
- **Wall clock.** Measured by running the real hook as a subprocess (through `_run.sh`) against a copy of the 5.8 MB eval snapshot, 98 prompts, Ollama warm.

  | Path | p50 | p95 |
  |---|---|---|
  | Full | 1.29 s | 1.67 s |
  | Disabled / trivial / killed | ~70 ms | 87 ms (one 454 ms outlier) |

  - In-hook retrieval after imports is p95 ~0.29 s. Process start plus the lancedb import is about 1 s.
  - The metrics' `ms` now counts from process start, so doctor sees the real figure.
- **Decision.** The target was p95 ≤ 800 ms warm, so `user_prompt_inject` stays **off** by default.
  - The precision target is met in-sample but not cross-suite, which is a second reason.
- **Option for the user.** A resident query process (for example the flush daemon serving a Unix socket) would cut the full path to roughly the in-hook figure.
  - Not built; it is for the user to decide.

### 5.4 Cheap Stop, one distill per segment
- **Capture.** Stop, SubagentStop, PreCompact and the new SessionEnd hook write an event holding the transcript byte offset and the scrubbed, `<private>`-stripped last assistant message. The hook no longer reads or parses the transcript.
  - SubagentStop uses `agent_transcript_path` when the harness sends it, so a subagent's own transcript is distilled instead of the parent's tail, 10 s after it stops. Without that path the event joins the parent's segment like a Stop.
  - A hook with neither a transcript nor a message writes nothing.
- **Segments** (`scripts/segment.py`). The daemon groups queued events by transcript. A segment closes at SessionEnd or PreCompact, after 10 min without a Stop (`segment_idle_seconds`), or at 20 queued Stops (`segment_max_events`).
  - The segment is read from a cursor up to the newest offset, whole lines only, at most `raw_tail_bytes`.
  - Cursors live in `~/.claude/brain/cursors/`, keyed by transcript path rather than project, so a `cd` mid-session does not re-read the session.
  - An event at or below the cursor reads nothing, so a crash between committing the cursor and deleting the events cannot re-distill. Only a file shorter than the cursor is read from 0.
  - It is tagged, scrubbed and packed into windows of 48,000 chars, one distill call each. That is one call for a normal segment; past 3 windows the oldest are skipped and logged.
  - On the Ollama backend, windows are at most 24,000 chars, because it distills with `num_ctx` 16384 and silently drops input past that. The Claude backend gets the full window. Only the test-only passthrough backend truncates.
  - The cursor moves only after the segment is stored or found empty. A failed distill re-reads the same range.
  - If the transcript is gone, the last messages are distilled as `[claude]` text, so a forged `[user]` tag cannot raise their trust.
  - Pre-v0.7 queue files keep their inline excerpt and the old per-kind debounce.
- **Daemon lifetime.** The daemon no longer counts idle time while any event is queued, so the 300 s idle exit cannot strand a 10 min segment.
- **Cost.** Before: one distill per debounce batch (30 s after the last Stop), re-reading the last 16 KB each time, so overlapping text was distilled again. After: about one call per segment, and each byte of the transcript is distilled once.
- `tests/smoke.sh` gets `segment_idle_seconds = 3`. It was not run, because it writes to the live `~/.claude/brain`.
  - Instead, `test_daemon_end_to_end_one_chunk_cursor_and_idle_exit` runs the real `capture.py` and `flush.py` against a temp brain root. It checks for one chunk, one cursor and an idle exit.
- **Resume.** None of the 60 most recent transcripts mixes session ids, so `--resume` appears to append to the same file and its cursor carries over. No seeding at SessionStart was added.
- **Notes for 5.6/5.7.** A PreCompact segment can now be up to 3 sonnet calls against the 60 s wait, so the compact summary will often be late and the raw digest must carry the restore. A failure on window 2 discards window 1's distill and is retried every second; the backoff in 5.7 matters more now.

### 5.5 One distill call per window, batched conflict judge
- **JSON distill.** The three distill prompts now ask for `{"bullets": [{"source", "section", "text", "salience"}]}`. One call per window returns the facts, their sources and their salience; `{"bullets": []}` means nothing to store.
  - `transcript.split_output` reads the reply. It strips a code fence and takes the outermost `{...}`.
  - A reply that starts like that JSON but does not parse (cut off at the token limit, or a stray character) keeps only its complete bullet objects and logs a warning. It is never stored as text. This is not retried yet, because without the 5.7 backoff a retry would run every second.
  - Any other reply goes to the tagged-markdown parser (`split_summary`), and `[no findings]` still means empty.
  - On Ollama, distill calls send `"format": "json"`. Merge and salience calls do not.
  - A bullet's source counts only if that source is present in the segment. Otherwise, or when the source is missing or unknown, the bullet takes the least-trusted source present. That floor is never `user`: a line the model did not attribute was not typed by the user. `split_summary` uses the same rule.
  - Sections (`Decisions`, `Files touched`, …; `Task` / `Findings` for subagents) become `###` headings inside each trust group.
  - A group's salience is the highest salience among its bullets, clamped to 1–10, and goes straight to `_store_chunk`. The web/tool group is capped at 5, because that text could ask for a high score. Nothing ranks by salience today except `migrate_recover_orphans`. A reply without salience (markdown fallback) uses the length/novelty heuristic as before, so the separate LLM salience call is never needed.
- **Batched conflict judge.** `flush._run_conflict_judges` collects the candidate pair of every chunk stored from a segment and judges them in one call.
  - Candidates come from the same cosine gate (0.85) and `may_supersede` guard as before. The segment's own new chunks are excluded, so two new chunks are never judged against each other.
  - One pair goes through `judge_conflict`, unchanged. More go through `judge.judge_conflicts` with `prompts/judge_conflict_batch.md`, which returns a JSON array of `{pair, verdict}`.
  - The pairs reach the model as a JSON array, so a memory cannot forge another pair's header.
  - Pairs whose new chunk has web/tool text are judged in a separate call from all-trusted pairs, so low-trust text never shares a prompt with a pair it could sway. A typical segment still makes one call.
  - A missing, unknown or unparseable verdict is DEFER, so nothing is written. An old chunk is superseded at most once per segment.
- **Deferred.** Reconsolidation (`ask("merge")` when a new chunk is near-identical to an old one) is still one call per merge. Merges are rare, and batching them would mean holding inserts until the merge reply arrives. Revisit if the eval shows them in the hot path.
- **Tests:** `tests/test_v07_distill_json.py` (9 tests):
  - the trust split with sections, max salience and the low cap;
  - the source clamp (never `user`);
  - empty, legacy and cut-off replies;
  - the prompts' placeholders, and Ollama `format: json` for distill only;
  - distiller salience stored end to end;
  - batch-judge parsing, failure and unforgeable pairs;
  - one judge call per segment without intra-segment candidates, and low-trust pairs in their own call.
- 543 tests pass.

### 5.6 PreCompact returns at once; session-scoped restore
- **PreCompact** queues its event, writes a digest and returns. The 60 s wait for the distill is gone, and the hook timeout drops from 120 s to 10 s. The segment is distilled in the background like any other boundary.
- **Digest** (`scripts/compact.py`, `sessions/<sid>.compact.json`, mode 0600): the newest `compact_digest_chars` (6,000) of the last 256 KB of the transcript, up to the event's offset.
  - It holds only `[user]` and `[claude]` segments. File, tool and web text is dropped, so nothing a tool fetched is replayed into the compacted context.
  - The segments are private-stripped and defused by the transcript parser, then scrubbed. The restore entity-escapes them again inside one `<brain-memory source="transcript">` block.
  - Without a transcript, the last assistant message is used, as `[claude]`.
  - A digest older than a day is dropped on read. The ledger prune also removes them after 7 days.
- **Restore** (SessionStart, source=compact). The restore is now scoped to the session: only a pre_compact chunk with this `session_id` and `valid_from` at or after the digest is used. Before, it took the project's newest pre_compact chunk, which could belong to another session open in the same repo.
  - If that summary is stored, it is restored and the digest is deleted.
  - Otherwise the digest is restored. Since the distill now runs after the hook, that is the usual case.
  - The ledger is reset as before, and the restore also works for a project with no store yet.
- **Late summary.** While a digest exists, the prompt hook checks (one `stat`) whether the summary has landed. If it has, it injects the summary once, records it in the ledger and deletes the digest.
  - This is part of the compaction restore, so it is not gated by `user_prompt_inject` or the kill switch. `[retrieve] compact_late_restore = false` turns it off.
  - Its output is merged with any gated memory into one hook reply.
- **Landed gate (fixup).** A summary counts as landed only once the PreCompact event's queue file is gone. flush deletes a segment's events only after all of its chunks are stored, so a restore never injects half a summary.
  - A summary can be several chunks (windows × trust groups) sharing the segment's `valid_from`. All injectable ones are restored, up to 6. Tool and web chunks stay excluded, as for any auto-injection.
  - A segment that lands without a chunk (no findings, or merged into an older chunk) drops the digest. Nothing follows.
  - Chunk `valid_from` is the newest event's `enqueued_ts` (the PreCompact or later), in seconds like the digest `ts`, so a segment with earlier Stops still matches.
- **Tests:** `tests/test_v07_compact.py` (6 tests). The real `capture.py`, `flush.py` and `inject_context.py` processes run against a temp brain:
  - the digest (escaped, no tool text, no private text, no secret, mode 0600) restored after compaction, then the late summary injected exactly once;
  - session scoping: another session's summary is never restored;
  - Stops followed by a PreCompact in one multi-window segment, then a second compaction in the same session that restores its digest, not the first summary, until its own summary lands;
  - the landed gate;
  - stale and invalid-id digests;
  - the PreCompact timeout.

### 5.7a A failure is retried, never forgotten
- **Strict replies.** Outside passthrough, a distill reply that is not `{"bullets": [...]}` is a failure, never "no findings". Before, prose or a refusal fell through to the markdown parser and could be stored, or end the segment with nothing. `[no findings]` and `{"bullets": []}` are still empty. A cut-off reply keeps its complete bullets.
- **Progress per window** (`segment.plan`, `Pass`). Windows are packed from whole JSONL lines, and each knows the byte offset after its last line.
  - flush stores one window, then moves the cursor past it and deletes the events whose offset it passed. A failure in window 2 keeps window 1 stored and committed, and the retry starts at window 2.
  - A pass reads `raw_tail_bytes` oldest-first and takes at most `segment_max_windows` windows. The rest waits for the next pass. Before, the oldest bytes and windows over the cap were dropped. A single line over the byte cap is read whole.
  - A pass ends at the first boundary event (SessionEnd, PreCompact), so turns after a compaction never join its summary. Events of the same second sort by kind in the queue, so pass membership goes by offset, not file order.
  - Without a transcript, and for pre-v0.7 events, a pass is all or nothing as before.
- **Retry with backoff** (`scripts/pending.py`). A failed segment gets `<project>/pending/<sha256(group)[:16]>.json` (mode 0600): attempts, first and last failure, next try and a short error. No transcript text.
  - Backoff is `retry_base_seconds` (60) doubling to `retry_max_seconds` (3600). There is no last attempt.
  - The daemon skips a segment while it backs off, and a segment that is only backing off does not keep the daemon alive. The next capture respawns it; Phase 7 doctor shows `pending.backlog()`.
  - A segment that succeeds clears its state.
- **Fixup: no pass can spin.**
  - A pass that read everything below its events (not capped by bytes or windows) finishes all of them on its final commit. Before, an event whose offset lay past the last whole line never finished: a line still being written, or a transcript rewritten shorter. The daemon then re-planned the segment every second and never idled out. The cursor stays at the last whole line, so the partial line is read later.
  - A pass that raises now backs off like a failed one (`error: <type>`). Before, it was retried at 1 Hz, with a paid distill call each time.
  - A pass that finishes no event and does not move the cursor backs off too (`no progress`), so a future bug cannot pin the daemon.
  - A window whose reply is invalid `skip_invalid_after` (5) times in a row at the same cursor is skipped. "Never give up" is right for transient failures. But a deterministic bad reply, such as an injected "answer in prose" in a tool result or a refusal, would block every later window of the session, including the compaction summary. The skip is recorded in `<project>/pending/skipped.jsonl` (group, path, byte range, error, no text; mode 0600) for doctor and a later re-run. A transient failure in between resets the count.
- **Removed:** `transcript.windows` (dropped the oldest windows) and `segment.texts`. `segment.read_range` stays for the compaction digest.
- **Tests:** `tests/test_v07_retry.py` (7): strict replies; a garbage reply goes to retry with no text in the state, then succeeds; a failed second window keeps the first; backoff and the backlog; the pass boundary, including same-second ordering; a capped pass skips nothing across passes; the daemon idles out past a backing-off segment. Fixup (4 more): a partial last line and a truncated transcript finish their events; an invalid reply for the same window is skipped and recorded; a raising pass backs off; real `capture.py` and `flush.py` with an unreachable backend exit, keep the event and cursor, and write the retry state under the key the daemon scans. The flush tests now mock JSON replies.

### 5.7b Distill fallback chain
- `[distill] fallback = []` (default off) lists backends to try, in order, when the primary returns nothing: `claude_code` or `ollama`. `passthrough` and unknown names are ignored with a warning. A silent fallback to raw transcript text would defeat the distill.
- Only `distill()` falls back (`call(..., backend=)`). The conflict judge, dream and `/remember` use the primary backend.
- A fallback is tried only when a backend returns nothing. An invalid reply is not retried on another backend in the same pass; it goes to the retry and skip path of 5.7a.
- Strict reply checking still keys off the primary backend. That stays correct because every backend that may answer in the chain is strict.
- Windows are planned before the distill call, so with `ollama` anywhere in the chain they are sized for its context (24,000 chars). Claude then gets about twice as many calls, each smaller.
- **Tests:** 2 more in `tests/test_v07_retry.py`: the chain order and refusals, the window width, and fallback only on an empty reply.

### 5.7c An embedder outage keeps the distill
- **Store without a vector:** `[embed] store_without_vector = true` (the default). When the embed fails, the chunk is stored with `vector = NULL`. The window commits, so the distill (the costly call) is not repeated.
  - Salience comes from the distiller, or 5 when there is none.
  - Reconsolidation, backlinks and the conflict judge are skipped at insert, because they need the vector. A near-duplicate may stay until dream merges it.
  - `<project>/pending/embed.mark` (it holds the cwd) marks the project.
  - Off: the embed failure fails the window, as in 5.7a.
- **LanceDB check (0.30.2):** null vectors are accepted. Hybrid search still returns the rows through FTS, an ANN index builds, and `where("vector IS NULL")` plus `update()` backfill them.
- **Backfill (`flush._backfill`):**
  - The daemon loop runs it at most every `backfill_interval_seconds` (60). Each round takes up to 20 null rows per marked project.
  - The first embed failure ends the round, so a down embedder costs one probe per interval, not one per chunk.
  - Embedded rows get backlinks and one conflict-judge pass per kind, with their stored provenance. Quarantined and superseded rows are skipped.
  - The mark is removed once a round finds fewer than 20 rows.
  - A failed `update` (for example a write conflict with dream) ends the round as `down` and is retried. Only an embed failure with a working probe marks a row as bad.
- **Pending work does not keep the daemon alive.** `dream.py` now starts the flush daemon (`capture._ensure_daemon`) when `pending.backlog` or an embed mark exists, so retries and backfills run at least nightly. The flush main-loop comment that promised this is now true.
- **Readers:** every reader of stored vectors (`effects`, `dmn`, `dream`, `inject_state`, `backlinks`, `flush`) already skips a None vector. Checked, no change needed.
- **Fixup (advisor review):**
  - **Bad rows:** one bad row no longer blocks every project. When a row fails, a probe text is embedded. If the probe works, the row is bad (too long, rejected): its id goes to `pending/embed_skip.json`, it keeps its NULL vector and stays searchable by keyword, and the round goes on. If the probe fails, the embedder is down and the round stops.
  - **Throttle:** only after a failure. `_backfill` returns `down`, `more` or `done`, and drains up to 200 rows per call. On `more`, the loop calls again on the next tick, so a backlog left by an outage drains in one daemon run instead of over many nights.
  - **FTS:** `refresh_fts` runs after each batch of updates. In LanceDB 0.30.2 the updated rows stayed findable without it (unindexed rows are flat-scanned; a mutation check confirmed this, so the test does not guard the call). It is kept because the docstring records crashes on unindexed rows, and its `optimize()` compacts the per-row update versions.
  - **Dream:** it starts the daemon after its pass (`finally`), not before, so the daemon's writes do not race dream's supersede writes. `_ensure_daemon` uses `start_new_session=True`, so the daemon outlives the launchd job.
  - **Real embedder:** checked against a dead endpoint (`127.0.0.1:9`, no fake embed). `embed()` raises, and the chunk is stored with a NULL vector, never a garbage one.
- **Tests:** 7 in `tests/test_v07_embed_backfill.py`:
  - store without a vector: the segment finishes, salience is 5, nothing is linked or judged, the mark is set, and FTS still finds the row;
  - one probe while the embedder is down, then embed, link and judge, and the mark clears;
  - with the flag off, the segment is retried;
  - dream starts the daemon only when retries are pending and the plugin root exists;
  - updated rows are found by FTS and by the hybrid `retrieve.search`;
  - a rejected row is skipped while others embed;
  - a long backlog returns `more`, then `done`;
  - a subprocess with the real embedder at a dead endpoint stores NULL and sets the mark.
- **Phase 6 doctor:** report `pending.embed_marks()` and `embed_skips` next to `backlog` and `skipped`.

## Phase 6 — launcher, scope and project key (2026-10-26) ✅

### 6.1 One launcher
- `hooks/hooks.json` and `.mcp.json` start from `${CLAUDE_PLUGIN_ROOT}` only, without guessing the newest directory under `~/.claude/plugins/cache/`. A cache that still held an old version could otherwise run stale code.
- Each hook command begins `[ -x "${CLAUDE_PLUGIN_ROOT}/scripts/_run.sh" ] || exit 0; exec …`. If the root is unset, the command would be `/scripts/_run.sh`, so the guard sits in the command, not only in `_run.sh`.
- **Kept:** the cache fallback in `commands/*.md`. It was added in 6bd1b75 because a slash command's shell does not always inherit `CLAUDE_PLUGIN_ROOT`.
- Checked (W3): every `claude -p` call goes through `cli.py` with the pinned working directory.

### 6.2 Scope
- **`[scope] exclude`** defaults to `~`, `~/Downloads`, `~/Library`, `~/.claude` and `/tmp`. `~` and `/` match only exactly; every other entry matches the directory and everything below it.
- **`include_only`**, when set, limits capture to the directories under its entries.
- **Per project:** a `.biss-brain-ignore` file, or `.claude/brain.toml` with `enabled = false`, in the project or any parent.
- **Shell check:** `_run.sh` checks `capture.py` and `inject_context.py` against `<brain>/scope.cache` and the opt-out files before Python starts, and never reads stdin. An excluded hook exits in 11 ms median (12 ms p90, 20 runs), against the 20 ms target.
- **Python check:** `scope.py` writes the cache when its rules change and checks again itself, so a missing or stale cache costs one Python start, never a wrong capture.
- This replaces capture's earlier guard, which only skipped `$HOME` and `/`.

### 6.3 One key per repo (D3)
- `project_key` hashes the main checkout of the repo holding the cwd. Subdirectories, `.claude/worktrees/`, `.trees/` and worktrees outside the repo share one store.
- `common.repo_root` reads `.git` (`gitdir:`, then `commondir`) without spawning git. `core.repo_root` uses it too, so core memory and the store agree.
- **Edge cases:**
  - A submodule (no `commondir`) is its own project.
  - A bare repo, a directory outside any repo, `$HOME` and `/` keep the realpath key. A dotfiles repo in `$HOME` never swallows every project below it.
- **No migration:** the D8 fresh start rebuilds the store, so no existing keys move. The eval snapshots keep their recorded hashes.
- **Tests:** `test_v07_scope.py` (9) and `test_v07_project_key.py` (6) run against real git worktrees, submodules and bare repos.

## Phase 7 — brain mechanisms: ablate, keep or retire (2026-10-26) ✅

### 7.1 Reconsolidation gated HiMem-style
- A labile neighbour above `merge_cosine_threshold` is merged only when it was used within the labile window *and* the new text revises it: at least `revise_min_novelty` (0.2) of its content terms are new.
- A restatement is folded into the used memory without the `ask("merge")` CLI call. The fold still refreshes `last_accessed` and combines provenance as a merge would.

### 7.2 Ablation and defaults
- **Tooling:**
  - `scripts/eval/ablate.py` replays the suite on snapshot copies, with the post-retrieval effects on, off and followed by dream 1c, and times `apply_post_retrieval`.
  - `run_eval.py` gains a `no_trust` variant.
- **Results:** `docs/eval/v0.7-ablation.md`. Run files are under `~/.claude/brain-eval/runs/phase7_*.json`.
- **Retired (code kept, default-off):**
  - RIF: real ΔMRR −0.105, CI [−0.187, −0.035], about 170 ms per read.
  - The usage boost in nightly decay: −0.018 real, −0.019 synthetic, no gain.
- **Kept under the rule:**
  - decay in ranking (neutral, free);
  - STDP, backlinks and DMN, which are graph tools only (no LLM).
- **Kept outside the rule** (neither was on the Phase 7 list):
  - hybrid retrieval: neither CI excludes 0 and it costs ~37 ms, but BM25 is the fallback when the embedder is slow and the only search over rows without a vector;
  - the provenance multiplier: a safety control; on the synthetic suite poisoned top-1 goes from 0 to 11 without it.
- **Not measured, defaults kept, user decision:** reconsolidation (on, gated), conflict sweep, session arcs, global promotion and rerank.
- **Snapshot limits:** the v0.6 snapshot has no taint and no summary rows, so `no_trust` and `summary_first` are zero by construction on the real suite. Their verdicts rest on the synthetic suite.
