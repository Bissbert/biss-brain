finding:
  id: "F-002"
  title: "Hypothesis quarantine filter absent from all three retrieval paths"
  severity: "high"
  category: "security"
  description: >
    Doc 04 §D.3 and 99-cross-cutting §6 Invariant 2 require that every retrieval
    path adds `kind != 'hypothesis'` to its WHERE clause. None of the three paths
    implements this filter:
      - `recall.py:414` builds `where_parts` with only `project` and `superseded_by`
      - `inject_context.py:388` constructs `where_sql` identically
      - `mcp/server.py:212` does the same
    All three pass through `kind != 'hypothesis'` only when the caller explicitly
    passes `--kind` or a `kind` argument matching a non-hypothesis value. Absent
    that argument, `kind=hypothesis` chunks are returned in normal recall results.
  location: >
    scripts/recall.py:414-419,
    scripts/inject_context.py:388,
    mcp/server.py:212-216
  evidence:
    - "grep 'hypothesis' in all three files yields zero WHERE-clause hits"
    - "where_parts = [f\"project = '{proj}'\", \"superseded_by = ''\"] — no kind filter"
  impact: >
    Quarantined hypothesis chunks (kind='hypothesis', consolidation_round=0,
    never user-promoted) are injected into context on normal recall, violating
    the quarantine invariant and potentially influencing code generation with
    unvalidated speculative claims.
  recommendation: >
    Add `"kind != 'hypothesis'"` to `where_parts` / `where_sql` in all three
    files as a permanent non-optional filter, independent of the `--kind` argument.
  status: "open"
  metadata:
    builder: "B3 (recall), B6 (MCP)"
    spec_ref: "doc 04 §D.3, 99-cross-cutting §6 Invariant 2"

```yaml
finding:
  id: "F-003"
  title: "DMN and dream.py drainers have divergent drained=1 semantics"
  severity: "medium"
  category: "quality"
  description: >
    `dmn.py:_drain_edge_bumps` marks ALL undrained bumps as `drained=1` after a
    tick, including those below `co_retrieval_min_count` (line 375: UPDATE WHERE
    project = ? AND drained = 0). `dream.py:_stage_nrem2_edge_drain` only marks
    the pairs it actually promotes (WHERE project = ? AND chunk_a = ? AND chunk_b
    = ? AND drained = 0). This means:
      a) Bumps below threshold seen by DMN are permanently consumed without ever
         producing an edge, even if more bumps accumulate later in the same day.
      b) The two drainers have different contract semantics for sub-threshold rows.
    In addition, `dmn.py:_add_typed_edge` is a private re-implementation
    (lines 290-321) instead of importing `backlinks._add_typed_edge`.
  location: "scripts/dmn.py:372-376, scripts/dmn.py:290-321"
  evidence:
    - "dmn.py:375 'UPDATE edge_bumps SET drained=1 WHERE project=? AND drained=0'"
    - "dream.py:1102 only marks the specific (chunk_a, chunk_b) pair as drained"
    - "dmn.py:290 defines its own _add_typed_edge without importing from backlinks"
  impact: >
    Low-frequency co-retrieval pairs that accumulate bumps slowly (e.g. 1 bump/day,
    threshold=3) will be permanently drained without an edge after the first DMN tick,
    causing them to never graduate to a `co_occurs` edge regardless of future bumps.
    The helper duplication creates the same silent-drift risk as F-001.
  recommendation: >
    1. Change dmn.py:_drain_edge_bumps to only mark rows that are in the promoted set
       as drained=1, mirroring dream.py's per-pair behaviour.
    2. Remove dmn.py's private _add_typed_edge; import from backlinks.
  status: "open"
  metadata:
    builder: "B5 (DMN)"
    spec_ref: "99-cross-cutting §B, 05-impl-research-orchestration §STDP"
```

    Change to: UPDATE chunks SET superseded_by = ? WHERE id = ? AND project = ?

## Dimension Verdicts

### A. Test Coverage and Integrity
81 unit tests pass. `test_reconsolidate_preserves_distinct_facts` genuinely verifies
both source facts survive in LanceDB (checks `"structlog"` and `"Sentry"` in stored
text). Parse-error fallback for salience and distill are tested. No test for the
`judge_with_project_context` R2 guard on a live call (covered by code inspection only).
Gap: three integration tests absent (F-006).

### B. Helper Reuse
`_compute_decay` duplicated in dream.py (F-001). `_add_typed_edge` duplicated in dmn.py
(F-003). Four post-retrieval helpers duplicated in mcp/server.py (F-005). All other
required helpers (`load_config`, `project_key`, `open_meta`, `hybrid_search`,
`now_unix`, `_fake_embed`, `write_backlinks`, `_load_prompt`, `_render`, `distill`,
`judge_conflict`, `parse_related_ids`) are correctly imported from their canonical modules.

### C. STDP Race Conditions
Both drainers use `BEGIN IMMEDIATE` and filter on `WHERE drained=0`. Double-promotion
is structurally prevented. However, dmn.py drains sub-threshold rows to drained=1 while
dream.py does not — this is a semantic divergence (F-003), not a data race.

### D. Reconsolidation Fact Preservation
`test_reconsolidate_preserves_distinct_facts` does verify both facts survive: it fetches
the merged chunk from LanceDB and asserts `"structlog" in merged_stored` and
`"Sentry" in merged_stored`. The test uses a deterministic stub that returns both facts,
which is the correct approach. `prompts/reconsolidate_merge.md` contains all six hard
constraints from doc 04 §C.1 (verified).

### E. Drift Gate
`_try_reconsolidate` in flush.py enforces `drift_max = 0.12` at line 297 (hard-coded,
not config). `test_drift_gate_rejects_hallucinated_merge` creates an orthogonal vector
(drift=1.0) and asserts `result is None`. Gate is correctly implemented and tested.

### F. Performance Budget
RIF in recall.py runs O(|retrieved| × top_n) sub-queries. With default `top_k=5` and
`top_n=10`: 5 retrieved × 10 neighbours = 50 sub-queries per chunk, giving 50×10=500
total ANN calls worst-case. The in-code comment bounds this at ≤100 ms on a 1k-chunk
fixture with a note to go async beyond 5k chunks. No quadratic cost path is visible.
The 10k-chunk scenario would push to ~250 sub-queries (25 results × 10), which could
exceed the 200 ms budget at scale — acceptable for v0.5 with the documented caveat.

### G. Cross-Stream Integration
The three integration tests are absent (F-006). Recommendation: write them before
Security review. This is necessary because the Security reviewer's charter explicitly
checks cross-path invariants that only exercise under end-to-end conditions.

## Verdict

**BLOCK**

F-002 (hypothesis quarantine filter absent from all retrieval paths) is a high-severity
security invariant violation. Quarantined speculative content can be injected into model
context on every normal recall, violating a core safety invariant of the architecture.
This must be fixed before Security review.

F-001, F-003, F-004, F-005, F-006 are medium/low findings that do not individually block
release but collectively represent significant technical debt. After F-002 is fixed, the
release posture changes to **PASS-WITH-WAIVERS** for the remaining mediums (F-003, F-004,
F-006 require user sign-off).
